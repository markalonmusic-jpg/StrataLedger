# Password recovery design (DESIGN, NOT BUILT)

**Date:** 2026-11-12 · **Status:** design for review. Nothing here is built.

**Owner decisions this design follows:**
* v1.0 ships two recovery paths:
  1. an Admin or the Master resets a regular user's password;
  2. every regular user gets personal backup codes.
* Email is an optional add-on with the lowest priority, used only when a sending mailbox is configured.
* Authenticator apps (TOTP) come in v1.1, after everything else works.
* **Passwords are never emailed.** Hashes cannot be turned back into passwords, and a password in a plain email
  is unsafe.

Read with:
* `modules/services/auth.py` (`login`, `change_password`, `recover_master`, the throttle);
* `modules/services/passwords.py`;
* `modules/services/users.py` (`reset_password`, `authorize_reset`);
* the first-run screen (S10, `first_run_model.py`);
* `platform_support.copy_secret_text`;
* docs/audit_readiness_design.md (keys, K1-K18) and docs/roles_permissions_design.md;
* CLAUDE.md backlog item 11.

## 0. What exists today (the starting point)

* **Passwords:** scrypt (N=2^15, r=8, p=1), a 16-byte salt per user, one self-describing string, compared in
  constant time. The policy is 12 to 1024 characters (`passwords.check_password_policy`).
* **Sign-in throttle:** per username in `login_throttle`. After 5 failures the account locks for 30 seconds,
  doubling with each further failure up to 15 minutes. Unknown usernames are throttled exactly like real ones,
  and the message is always the same: "Invalid username or password".
* **Master recovery code:**
  * 160 random bits, shown once at first-run.
  * Stored only as a scrypt hash in `master_recovery`.
  * `recover_master(code, new_password)` sets a new Master password and issues a new code at once, throttled
    under its own key.
* **Admin reset:** `users.reset_password(session, target, new_password)`.
  * The Admin types the temporary password.
  * The user must change it at next sign-in (`must_change_password`).
  * It needs `company.users.manage` in a company where the target has access.
  * An Admin can reset neither the Master nor a user who is Admin anywhere; the Master can reset anyone.
  * It is logged as "Password reset" in `auth_event`.
* **Sessions:** a `Session` is plain data held by the running app. Services re-read the user on every call
  (`auth.active_user`), so deactivating a user takes effect at once. No session table exists.
* **Secret-safe copy:** `platform_support.copy_secret_text` puts a secret on the clipboard and asks Windows to
  keep it out of clipboard history and cloud sync (requested, not guaranteed; the screen says so).

## 1. Admin and Master reset of a regular user (v1.0)

* **Who:**
  * New permission `user.reset_password` (sensitive, module Company), seeded to Admin; the Master holds every
    code. It replaces `company.users.manage` as the reset gate, so a role can manage users without resetting
    passwords.
  * The scope rule stays as built: an Admin may reset a regular user who has access to a company where the Admin
    holds `user.reset_password`.
  * An Admin can never reset the Master, nor a user who is Admin anywhere (only the Master can).
  * Nobody resets their own password this way; they use "Change password" or backup codes.
* **Temporary password generated by the app, not typed by the Admin:** 16 characters from an unambiguous
  base32 alphabet in groups of four (80 bits). It is shown once, on one screen, with:
  * the secret-safe Copy button;
  * a clear "I have handed this over" button that closes the screen and clears the clipboard if it still holds
    the password (the first-run pattern);
  * the warning that a copy may remain in clipboard history on some systems.
* **Delivery:** the Admin gives it to the user in person, by phone, or in the company's own chat. The screen
  says so and never offers to email it.
* **Expiry:** 72 hours (*confirm*; new `app_user.temp_password_expires_at`). Signing in after expiry gives:
  "This temporary password has expired. Ask your administrator for a new one." Only someone who typed the
  right temporary password sees that message, so it reveals nothing to a guesser.
* **Forced change** at the next sign-in (existing `must_change_password`). Nothing else works until it is
  changed (existing `PasswordChangeRequiredError`).
* **Backup codes** are not touched by an Admin reset (*confirm*, Q7).
* **Audit:** `auth_event` "Temporary password issued" (actor, target), then "Password changed" when the user
  sets their own.

## 2. Personal backup codes (v1.0)

* **Who:** every regular user. The Master has the recovery code instead (section 3).
* **When issued:**
  * Automatically, right after the user's first forced password change (their first sign-in): the next screen
    shows the codes before the user reaches the app.
  * Reissued at any time by the user (who must enter their current password) or by an Admin with
    `user.reset_password` for that user.
  * Reissuing invalidates the whole old set at once.
* **Shown once:** 10 codes on one screen with:
  * Print, which opens the system print dialog on a plain page (no network);
  * Save as a text file to a location the user picks;
  * the secret-safe Copy;
  * a required "I have saved these codes" box.

  The screen advises: "Keep them somewhere other than this computer." When an Admin reissues, the Admin sees
  the codes once and hands them over like a temporary password.
* **Format and strength:** each code is 10 characters from the base32 alphabet (A-Z, 2-7), shown as two groups
  of five (`K7QXM-2RD4P`). That is 50 random bits, from `secrets`. Input is normalised: case and spaces are
  ignored and dashes are optional.
* **Storage:** a new master table `user_backup_code`:
  * columns: user_id, set_id, slot 1-10, `code_hash`, `used_at`, `issued_at`, `issued_by`;
  * `code_hash` is a scrypt hash with its own 16-byte salt, the same function as passwords;
  * the plain code is never stored and never logged;
  * append-only except `used_at`, which is set once; a reissue marks the old set superseded.
* **Using a code** ("Forgot password" on the sign-in screen):
  1. The user enters username, one backup code, and the new password twice, on one form and in one submit.
  2. The service hashes the input against **all 10 slots** of the user's current set. Used or superseded slots,
     and an unknown username, check against a dummy hash, so the work and the timing are the same in every case.
  3. A match marks that slot used, sets the new password under the policy and ends other sessions (section 5).
  4. The result shows "You have N backup codes left." At 2 left or fewer it adds a warning to make a new set
     (Settings > My account > Backup codes).

  The remaining count is also shown on the account screen.
* **Failure:** one neutral message: "That username and code do not match. Check the code and try again." It is
  the same for an unknown username, an inactive user, a used code or a wrong code.
* **Audit** (`auth_event`): "Backup codes issued" (actor, user, set id), "Backup code used" (user, slot, never
  the code), "Backup code failed" (the username as typed, like a failed login).

**Unrecoverable store: why scrypt per code, and what it costs**

| Store | Offline attack on a stolen master file | Cost per attempt here | Verdict |
|---|---|---|---|
| Plain SHA-256 of the code | 50 bits is about 10^15 hashes: roughly a day on one GPU per user | trivial | No: too weak offline |
| HMAC with a secret pepper (the installation key) | Infeasible without the key, but the key sits on the same computer (K1) | trivial | Not on its own |
| **scrypt, per-code salt (recommended)** | 2^50 attempts × about 50 ms of memory-hard work: infeasible | about 0.5 s (10 checks, always) | **Yes** |

Online guessing is bounded by the throttle (section 4): with 10 live codes, each guess has a 10 / 2^50 chance.
The constant 10 checks per attempt also slow automated guessing on the machine itself.

## 3. The Master

* **The recovery code is required for every Master password change**, not only a forgotten one (owner
  decision).
  * "Change password" for the Master asks for the current password **and** the recovery code.
  * "Forgot password" for the Master asks for the recovery code only (the existing `recover_master`).
* **Using the code always issues a new one at once.** It is shown once on the first-run style screen (Copy,
  print, "I have saved this code"), as `recover_master` already does. This is backlog item 11 together with
  "issue a new code after re-entering the password".
* **Step 1c dependency:** each time the recovery code changes, the installation key's recovery-wrapped copy is
  rewritten with the new code (audit design 2.7). The Master path is therefore built after Step 1c, or with it,
  in the same transaction as the code change. Otherwise the new code would not open the key.
* **No Admin path:** nobody can reset the Master, and the Master gets no backup codes. The recovery code is the
  only way back. The Master cannot reset their own password through the user-reset screen.
* **Lost code, forgotten password: no recovery. Say so plainly.** The sign-in screen's help text is: "If the
  Master password and the recovery code are both lost, the Master account cannot be recovered. Company files
  stay on this computer and in backups, but nobody can sign in as the Master." The first-run screen already
  says to store the code in two places (written down, and a password manager or safe), and the
  new-code screen says the same.
* **Audit:** "Master password changed" (with the code), "Master recovered" (exists), "Recovery failed"
  (exists), "Recovery code issued".

## 4. Abuse limits

* **Per account**, existing throttle keys:
  * password sign-in: the username;
  * backup-code attempts: `#backup:<username>` (`#` is never in a username);
  * the Master recovery code: `#recovery`.

  Each key gives 5 wrong attempts, then a cooling-off of 30 seconds that doubles per further failure up to 15
  minutes (*confirm*; these are today's values). A success clears that key.
* **Per installation:** a new key `#forgot-all` counts every failed recovery attempt (backup code or recovery
  code) for any username. It allows 20 failures in 15 minutes, then pauses "Forgot password" for everyone for 15
  minutes (*confirm*). Password sign-in is not paused by it. This stops spraying many usernames.
* **Wording:**
  * locked: "Too many attempts. Try again in N minutes." (`LoginThrottledError` already carries the wait);
  * paused for everyone: "Password recovery is paused for a few minutes after many failed attempts."

  Neither says whether the username exists.
* **No user enumeration:** one message per screen for every failure, as above. Unknown usernames are throttled
  and hashed like real ones (dummy hash), so the timing is the same where practical: scrypt dominates and is
  always run the same number of times.
* **Constant-time compares** everywhere (`hmac.compare_digest`, as `passwords.verify_password` does).

## 5. After any reset or recovery

* **Other sessions end.** Add a new `app_user.credential_epoch` integer, incremented in the same transaction by
  every password change, reset, backup-code use and Master recovery.
  * The `Session` carries the epoch it signed in with.
  * `auth.active_user` compares it on every service call. On a mismatch it raises a new `SessionEndedError`:
    "Your password was changed. Sign in again."
  * This ends every other window or Remote Desktop session (P1) at its next action, without a session table.
* **Audit entries** (`auth_event`, append-only): "Temporary password issued", "Password reset" (kept for the
  admin action), "Password changed", "Backup codes issued", "Backup code used", "Backup code failed",
  "Master password changed", "Master recovered", "Recovery failed", "Recovery code issued", "Recovery paused".
  The `auth_event.event_type` CHECK grows to match.
* **Password policy**, for every new password:
  * 12 to 1024 characters (built);
  * entered twice (the screen);
  * not only spaces (new);
  * not the username in any letter case (new: `check_password_policy(password, username=...)`).
* **Nothing secret** in logs, audit rows, exception messages or reprs: no password, temporary password, backup
  code, recovery code or hash. Events name the user and the slot only.

## 6. Optional email (v1.0 last, or v1.1)

Lowest priority; built only after sections 1-5 and Step 1c.

* **Service:** `modules/services/email.py`, a provider interface like the key provider:
  * `send(message)` with `to`, `subject`, `text`;
  * `SmtpProvider` now; a hosted provider (Azure Communication Services or similar) later, with no service
    changes (P5);
  * a fake provider in tests.
* **Settings screen** (installation level, Master only; *confirm* Q6). It holds:
  * server, port, the encryption mode (STARTTLS or TLS-on-connect; plain is refused);
  * username and from address;
  * a "Send test message" button.

  The SMTP password is stored as a keystore secret (Step 1c `KeyProvider`, a `get_secret(name)` alongside chain
  keys), never in a database row or a log.
* **Flows** (all neutral, all throttled, all audited):
  * **Forgot username:** email the username to the address on file. The screen always says "If that address
    belongs to an account, we sent the username to it."
  * **Emailed one-time code** instead of a backup code:
    * 8 digits, hashed (scrypt, salted), valid 15 minutes, 5 attempts, single use;
    * a new request cancels the old code;
    * the code is never a password and never reveals one.
  * **"Your password was changed" notice** after every change, reset or recovery, with "If this was not you,
    contact your administrator."
  * **Optional second check for the Master:** an emailed code in addition to the recovery code (off by
    default).
* **No email configured:** every screen that would offer email says "Ask your administrator" instead.
* **Confirm before building:**
  * **TLS:** Python `smtplib` with `ssl.create_default_context()` verifies certificates and host names, and
    the usual ports are 587 (STARTTLS) and 465 (TLS-on-connect).
  * **Microsoft 365:** the current state of SMTP AUTH and basic authentication; app passwords or OAuth may be
    required.
  * **Gmail:** app passwords or OAuth are required.
  * **Corporate relays:** some require no authentication on an internal relay; decide whether to allow it.
  * **Address on file:** whether `app_user.email` is verified anywhere (today it is not; a verification step may
    be needed before email recovery can be trusted).

## 7. Authenticator (TOTP), v1.1: hook only

The v1.0 design must leave these open:
* **Sign-in must be able to stop half-way:** `login` may return a "second step needed" state instead of a
  Session, without a breaking change to its callers. That state carries no Session and expires quickly.
* **Secret storage:** a per-user TOTP secret is an encrypted secret, wrapped like other keystore secrets, not a
  hash, because the app must compute codes from it. Enrolment shows a QR code once.
* **Recovery:** a lost authenticator is recovered with a backup code (section 2) or an Admin reset, which also
  clears the TOTP enrolment (audited).
* **Audit and policy:** event types "Authenticator enrolled", "Authenticator removed", "Second step failed".
  A company setting "require an authenticator" becomes a control (off by default).

## 8. SMS: not recommended

SMS codes can be intercepted by SIM-swap and number-porting fraud and by phone malware. They need a paid
third-party gateway and a network connection, which conflicts with the offline desktop product. They also
put phone numbers in the master database. Backup codes cover the same need offline and more safely. If the
hosted product ever wants a phone channel, it should be an authenticator or push approval, not SMS.

## 9. Threat model

| Method | Protects against | Does not protect against |
|---|---|---|
| Admin reset (temporary password, 72 h, forced change) | A user who forgot their password; the Admin never learns the user's own password | An Admin who abuses the power (audited, but possible); someone watching the screen or the clipboard while it is shown |
| Backup codes | Forgotten password with no Admin available; offline cracking of the stored codes (scrypt) | Lost or photographed printed codes (anyone holding a code and the username can reset); malware on the machine |
| Master recovery code | Forgotten Master password | Loss of both password and code (no recovery); someone who finds the written code |
| Throttle and installation pause | Online guessing and spraying across usernames | An attacker with a copy of the master file (offline: only the hash strength protects) |
| Session epoch | A session left open elsewhere after a reset | Someone already at the open window before the change (they are signed out only at their next action) |
| Email (optional) | Self-service without an Admin when a mailbox is set up | A compromised mailbox; unverified addresses |
| Not offered: emailed passwords, SMS | n/a | n/a (removed by design) |

Someone at the unlocked machine, with the user's Windows session, is outside what passwords can stop; the
setup guide's advice (lock the screen, BitLocker) applies.

## 10. Tests (written first in the build phase)

1. No password, temporary password, backup code, recovery code or emailed code appears in log files at DEBUG,
   in `auth_event`, `audit_log` (master and company), in exception messages or in reprs.
2. A backup code works once; the second use fails with the neutral message.
3. Wrong codes, codes from a superseded set, and expired temporary passwords all fail.
4. 5 wrong attempts lock that key; the cooling-off doubles; the per-installation pause triggers at 20 in 15
   minutes; a success clears the per-account key.
5. Enumeration: unknown username, inactive user, used code and wrong code give identical messages and run the
   same number of scrypt checks (spy).
6. Reissue invalidates every old code at once and is audited.
7. Session epoch: another Session of the same user fails with `SessionEndedError` after any reset, change or
   recovery.
8. An Admin cannot reset the Master or another Admin; a role without `user.reset_password` cannot reset.
9. The Master's password change requires the recovery code, and issues and returns a new code. With Step 1c,
   the installation key is re-wrapped (it opens with the new code and not with the old).
10. A temporary password expires after 72 hours (fixed clock) and forces a change before anything else works.
11. Policy: 11 characters refused, 12 accepted, 1024 accepted, 1025 refused; only spaces refused; the username
    in any case refused.
12. Email (when built): the code expires at 15 minutes, 5 attempts, single use; the "password changed" notice is
    sent; no-email-configured screens say "Ask your administrator"; a fake provider records messages and no
    real network is used.

## 12. Open questions, with proposed answers

1. **Temporary password expiry.** Proposed: 72 hours, as suggested.
2. **Admins resetting other Admins.** Today only the Master can. Proposed: keep it, so an Admin cannot take
   over another Admin's account.
3. **A new `user.reset_password` permission instead of `company.users.manage`.** Proposed: yes (sensitive,
   seeded to Admin), so managing users and resetting passwords can be split.
4. **A generated temporary password instead of one the Admin types.** Proposed: yes; the current API takes the
   Admin's choice, which is replaced.
5. **Backup code format and limits.** Proposed: 10 codes of 10 base32 characters (50 bits), scrypt per code,
   every attempt checking all 10 slots, warning at 2 left.
6. **Where email settings live.** The task says a company configures a mailbox, but user accounts belong to
   the installation (the master database). Proposed: installation-level settings managed by the Master,
   optionally shown to each company's Admin as read-only.
7. **Does an Admin reset invalidate the user's backup codes?** Proposed: no; the codes stay valid, and the
   user can reissue them.
8. **Throttle values.** Proposed: keep today's per-account values (5, then 30 s doubling to 15 min) and add the
   per-installation pause (20 failures in 15 minutes, 15-minute pause).
9. **Master changes always needing the recovery code.** Proposed: yes, as decided. Each change issues a new
   code and re-wraps the installation key, so the Master must save a new code every time; the screen says so
   before they start.
10. **Policy additions** (not only spaces, not the username). Proposed: apply to every new password from the
    build step on; existing passwords are not forced to change.
11. **Admin-reissued backup codes.** Proposed: the Admin sees them once and hands them over like a temporary
    password; the user is told to reissue their own set soon.
