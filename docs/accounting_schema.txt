==============================================================================
ACCOUNTING LIBREBASE - FULL SCHEMA (PLANNING DRAFT)
Date: 2026-11-09
Target: desktop application, SQLite database, one file per company
==============================================================================

CONVENTIONS
- Money is stored as INTEGER cents ($12.34 = 1234). Money fields end in _cents.
- Dates are text, ISO format YYYY-MM-DD. Timestamps are YYYY-MM-DD HH:MM:SS.
- Booleans are INTEGER 0/1. Percentages are REAL (e.g. 0.10 = 10%).
- PK = primary key.  FK -> table.column = foreign key.  (opt) = nullable.
- Posted records are locked. Corrections are made with reversing entries.
- Status/type value lists shown in [brackets] are suggested allowed values.


TABLE INDEX
 1. System and settings   schema_version, company_settings, app_user, audit_log
 2. General ledger        account_type, account, fiscal_period, journal_entry,
                          journal_line, bank_reconciliation

                          payment_allocation
 4. Imports and staging   import_source, import_batch, import_mapping,
                          staged_transaction, staged_line, time_entry

 6. Projects              cost_code, estimate, estimate_line, project,

KEY RULES AND CONSTRAINTS
==============================================================================
Where each rule is enforced (updated 2026-11-10, migration 002):
  [schema]        enforced by a CHECK, UNIQUE or trigger in migrations/*.sql
  [service layer] enforced later in the service layer (CLAUDE.md Phase 2),
                  when the feature is built; not by schema triggers
  [not enforced]  open gap, see docs/schema_audit.md

LEDGER
 1. An entry can be posted only if it has 2+ lines, total debits equal total
    credits, and its fiscal period is open.
    [schema] trigger journal_entry_require_balance_on_post: 2+ lines, each
    with exactly one non-zero side, total debits > 0 and equal to credits,
    period not closed (by period_id or by entry_date).
 2. Posted entries are locked: no editing, adding or deleting lines.
    Corrections use a reversing entry (reverses_entry_id).
    [schema] triggers journal_entry_lock_posted / _lock_delete_posted and
    journal_line_lock_*. A posted entry cannot be unposted, edited or
    deleted.
    Void = reversing entry (migration 003). A reversal sets
    reverses_entry_id (unique: one reversal per entry) and reversal_reason
    [Void, Accrual reversal, Correction]. It posts only if the original is
    posted and unvoided, it mirrors the original exactly (same accounts and
    tags, debits and credits swapped), and it is in an open period. Posting
    a Void reversal sets is_void = 1 on the original in the same statement;
    is_void cannot be set any other way. is_void is only a marker: reports
    never filter on it, because the reversal nets the original to zero.
    A void therefore never changes a closed period. [schema]
 Lines need an account (account_id NOT NULL). Entry and period dates are
 strict ISO YYYY-MM-DD (CHECK (col IS date(col))). [schema]
 3. Only postable, active accounts can receive journal lines.
    [service layer] (Phase 2; test marked expected-failure until then).
    Manual entries to controlled accounts (account.control_type) are also
    blocked in the service layer (decision 5).
 4. Closed periods block new postings.
    [schema] see rule 1.
 Migration 004 [schema]:
 - Every entry carries period_id (NOT NULL), the period that contains its
   entry_date; the service sets it. Periods are contiguous with no overlap;
   only the outer edges of the range move, and only while unused. Closing
   records closed_at/closed_by; reopening needs a logged reason [service
   layer].
 - Posting records created_by, posted_by and posted_at, and takes a gapless
   entry_number from entry_number_sequence. approved_by cannot be the
   creator; when approval is required (company setting, threshold; agent
   and import entries always) is decided by the service layer (decision 6).
 - An account with posted entries keeps its code, type, parent and
   control type. Every account has a type (five types are seeded).
 - journal_line tags (contact, project, cost code, deferral, batch,
   reconciliation) are real foreign keys. recon_id may change on a posted
   line only while its reconciliation is open; a completed reconciliation
   is locked. Dimensions on journal lines: journal_line_dimension.
 - Reports and v_gl_detail never filter on is_void (decision 1).
 Money: every *_cents column has CHECK (typeof(col) = 'integer') [schema].
 User references (created_by, approved_by, ...) in a company file hold the
 system_master app_user.user_id as a plain integer with no FK; SQLite cannot
 enforce keys across database files. app_user lives only in system_master.db.

IMPORTS AND STAGING
 Rules 5-10: [service layer].
 5. external_ref is unique per source, so re-importing a file cannot create
    duplicates.
 6. Staged lines must add up to the staged transaction amount.
 7. A batch posts only when every row is Approved and every bill payment is
    matched. Posting order: bills first, then payments.
 8. A payment cannot be approved until its matched bill is approved.
 9. Rejected rows stay in staging for the record and never post.
10. Staging rows never appear in ledger reports.

DEFERRALS
 Rules 11-14 and the payment_allocation "exactly one of" rule: [service
 layer], except UNIQUE (deferral_id, period_id) [schema].
11. Posted schedule lines lock. One schedule line per deferral per period.
12. Billed in advance: bill records debit prepaid / credit payable (expense)
    or debit receivable / credit deferred revenue (revenue).
    Paid in advance: the payment records the deferral; attaching the bill
    later creates NO new ledger entry (status "Covered by advance").
13. Sales tax is never deferred; only the revenue portion is.
14. Invoice lines on projects using percentage-of-completion or completed
    contract do NOT create deferrals.

PROJECTS
 Rules 15-20 (change order approval locks, snapshot locks, construction
 approvals): [service layer], except UNIQUE (project_id, period_id) on
 poc_snapshot [schema].
15. Revised contract value = sum of contract original amounts + approved
    change order revenue. Revised budget = original budget lines + approved
    change order cost lines.
16. Approved change orders lock. Fixes are made with a new change order.
    Change orders post nothing to the ledger by themselves.
17. A change order approved with an effective date in a closed period is moved
    to the first open period.
18. Percent complete = cost to date / (cost to date + est. cost to complete).
    Earned revenue = percent complete x revised contract value.
    Snapshots are cumulative, so mid-job changes are a catch-up in the period
    they take effect. Posted snapshots lock.
19. If estimated total cost exceeds revised contract value, the full expected
    loss is recognized immediately.
20. Progress invoices post to contract revenue; the period-end snapshot
    adjusts revenue to the earned amount, with the offset to the
    underbilled / overbilled accounts.
